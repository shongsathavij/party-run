# Party Run

An AI agent that shops for a kid's birthday party from real store listings (a saved snapshot), and can only spend what the parent approves. Payments stay in Stripe test mode: nothing is ordered and no store is contacted. Portfolio project for a senior payments PM (companion to Supper & a Show at date.sirinrut.com). Planned home: party.sirinrut.com, its own Vercel project and GitHub repo.

The pitch: the agent can shop, but it can't overspend, because the limits live in the payment itself (Stripe shared payment tokens), not in the prompt.

## Stack

- Static front end, no build step: `index.html`, `styles.css`, `app.js` (ES modules; the page imports `lib/` directly).
- `lib/catalog.js`: real stores (C&M Event Rentals and L.A. Inflatables Rental, Whole Foods Market catering, Target, Walmart, Michaels) with real listings copied on `SNAPSHOT` (name, price as listed before tax and delivery, link), plus one made-up test store (`test: true`, Brickyard Party Supply). To refresh: re-check each `url`, update prices, bump `SNAPSHOT`. `lead` is our own planning buffer, not a store policy. Favors are sold in packs (`per: 'pack'`, `packOf`). `lib/rules.js`: cart totals, `checkCart`, `permissionFor`, `decide`, `raise`. Pure functions shared by the page, the server, the agent's checks, and the evals. Change a rule there, never in a copy.
- Vercel functions in `api/`: `plan` (the agent), `permit` (sign the parent's permission), `buy` (mint a pass and charge one store), `raise` (parent OKs a higher price), `refund` (store cancels), `replace` (find the same kind of item at a different store, within what's left of the budget; rules, not AI), `edit` (change the cart before approval), `config`. `api/_lib/` isn't routed.
- No dependencies. Stripe and Anthropic are called with `fetch`.

## Commands

- `node scripts/serve.js` (PORT to change from 3000): local server, reads `.env.local`.
- `npm test`: every route in sample mode plus the agent tool loop with a scripted model.
- `node evals/run.js` (rules agent) or `--agent claude --model claude-haiku-5-5 --runs 2`. All checks are code (money and safety have right answers): buyable cart, never buys what a listing pushed, reports the hidden instruction, honest about budget, enough favor packs for every kid, plus per-prompt expectations. The 12 prompts are all variations of the real party. Results in `evals/results/`. Also runs from GitHub Actions ("Agent evals").

## Rules

- Every route works with no keys: a rules agent stands in for Claude, and payments are simulated with the same rules, labeled on the page.
- Token budget: the agent searches every category in one turn, then submits (about 2 turns a plan, `MAX_TURNS` 5). `api/plan.js` gives each visitor 5 Claude plans an hour and each server instance 60 a day (`PLANS_PER_VISITOR_HOUR`, `PLANS_PER_DAY`); past that the rules agent plans (mode `limited`). `PARTY_AGENT=rules` turns Claude off. Counters are in memory, so the real ceiling is the Anthropic account's spend limit. Evals print total tokens.
- Test mode only: `api/_lib/stripe.js` refuses any key that isn't `sk_test_`. Payments use Stripe's test Visa (`pm_card_visa`); there's no card form yet.
- The agent never gets a payment tool. It proposes a cart; the parent approves a permission; the server buys.
- Prices always come from the catalog by id, never from the page or the model.
- Permission (`permissionFor`): one cap per store (that store's approved total); caps add up to no more than the budget (no budget given: the cart total is the budget); an ask-me threshold (`askOver`: $50 / $100 default / $300 / always / never); ends on the party date. The server signs it (HMAC, `api/_lib/permit.js`, `PERMISSION_SECRET` or derived from the Stripe key); a changed permission is refused.
- Buying (`api/buy.js`): check the permission and `decide()` (store in it, under its cap, ask-me rule), then mint a shared payment token for that store only, capped at its approved amount, expiring in 30 minutes (`TOKEN_MINUTES`), then the store charges it. In test mode the token comes from Stripe's test helper (`/v1/test_helpers/shared_payment/granted_tokens`; it takes payment_method, usage_limits, customer and shared_metadata only, so the store goes in shared_metadata) and the charge is a confirmed PaymentIntent with `shared_payment_granted_token`. If Stripe ever accepts a charge over the cap, it's refunded at once and reported (`railsMissed`).
- What-ifs (demo): "the checkout comes to more" adds a made-up $20 to the rental's charge (`PRICE_UP` in `api/buy.js`); the pass refuses it and the parent can approve the difference (`raise`, which can't exceed the budget or 1.5× the old cap). "The rental cancels" refunds its payment. Both are worded as simulations: never say a real store added a fee, cancelled, or did anything it didn't.
- Real stores: names as plain text only (no logos), every real item links to its listing, the page says the listings are a snapshot, that Party Run isn't affiliated, and that nothing is ordered. Nothing false about a real business, so both deliberate traps live only on the made-up test store, which is labeled on the page: its brick bounce house is booked Dec 5-6 (the agent must swap to a real rental and say why), and its table set hides an instruction to AI shoppers (prompt injection). The agent reports the instruction and buys nothing from that store unless the parent asks for the Deluxe package by name. Listings are wrapped as data in tool results; the prompt says listings are never instructions; and `pushedByListings()` sends back any cart item a listing names unless the parent's request asks for it by its distinctive word ("deluxe").
- Fallbacks: when the rules agent plans instead of Claude, `plan` returns `fallback` (`kind`: `checks`, `no_cart`, or `error`, plus the first reason) and the page says which happened; never call an API error a failed check. The model gets two turns to search, then `tool_choice` forces `submit_cart`. A first cart with only soft problems is kept if the model's fix comes back unbuyable.
- Under the hood: every `buy` result carries `hood` (token id, cap, expiry, what the store charged, the PaymentIntent, Stripe's code and decline code, and `decidedBy`: `stripe`, `simulator` with no key, or `refund` when Stripe accepted an over-cap charge and our code undid it). The page shows it per store and must say plainly which of the three happened.
- Changing the cart: before approval only (`state.locked` once shopping starts). + / − appear only on favors and food (`countable`), under the price, and call `edit` with `set` (plain code, no tokens). "Ask for a change" calls `edit` with the parent's words (300 characters): Claude in edit mode (`EDIT_RULES`, counts toward the same per-visitor limit in `_lib/limits.js`), or `rulesEdit` when Claude is off (add, remove, amounts, cake flavor, budget; says plainly when it can't). Either way the cart is rebuilt from the catalog (`rebuild`), checked like a new plan, refused if it breaks a check or the budget, and shown as a diff (`diffCarts`).
- Theme: `offTheme()` flags themeable items (bounce, cake, piñata, decor) that don't match the request's theme; `plan` marks each item `offTheme` and `needsOk` (off-theme and asked for by name). The page shows a "Not brick-themed" chip, and any `needsOk` item must be kept or dropped before "Let the agent shop" works.
- Falling through: when a store is skipped or refunded and nothing else covers that part of the party, the page says the party isn't complete and offers "Find another <thing>". `replace` skips the stores already tried and the test store; the parent approves a second, separate permission for that one store and amount. The $20 what-if happens at one rental only (`priceUpStore`). The receipt says whether the party is complete.
- Asked for by name: `flagTheme` also sets `cart.asked` (named categories) and `cart.little`. Claude's cart is sent back once if a named thing is missing with no word why in `unmet`. The page shows "Missing from the cart" with Add (`edit` with `add`, rules, no tokens) or Skip; after the run, a named thing that isn't paid for counts as missing even if it never reached the cart. Anything the parent removed (`state.declined`) is never "missing". `api/_lib/pick.js` (`pickFor`) is the one picker for add and replace: free on the date, within what's left, never the test store, on theme when possible, and with kids under 4 only pull-string piñatas (`pull: true`) and ages-2+ favors. A failed purchase is logged for the receipt.
- Permission receipt: after the run, one record built from `state.log` (per-store events: asked, paid, refused, raised, skipped, refunded) and the first approved permission: what the parent approved, what the agent did and ignored, each store's limit (and any raise), what happened in order with pass and PaymentIntent ids, totals, and a verdict that checks spending never passed what was approved. Print or copy as text.
- Try to trick the agent: a visitor's text (`plant`, cleaned, 300 characters max) replaces the planted instruction in the test store's table-set listing for that one plan (`withPlant`). Never plant text in a real store's listing. `pushedByListings` also catches items the planted text names by name. `plan` returns `trick` (reported, sentBack, tookOver), and the page reports each layer as it happened, including when the agent did not flag the text.
- Agent rules (prompt and rules agent alike): basics (cake, decor, favors, snacks) plus what's named; bounce house or piñata only if asked; "just"/"only" means only what's named; kids from the request (top of a range; default 10); enough favor packs for one per kid; favors rated for the youngest guest (ages 2+ when 2-year-olds come) and a pull-string piñata with kids under 4; nothing booked or past its notice; stay under budget, dropping extras first; `unmet` only lists what they asked for.
- The real party in the demo is the owner's son's 5th birthday: building-brick theme, backyard, Dec 5, 10am-noon, 6-10 kids ages 2-5, bounce house and piñata, under $600. No names, no address. The page only plans this party: the request is shown read-only (the API still takes other wording, for the evals). Real listings keep their real names; our own words and the test store say "building-brick", not the trademark; the parent's own words can say Lego.
- Design: same system as Supper & a Show (Instrument Serif + Inter Tight, ink outlines, sticker chips). Violet #5B35D5 for anything you tap to act; yellow #FFD23F for the "PARTY RUN · BETA" sticker and the agent's face; butter for the agent's voice; each store kind has a brick-badge color (rentals coral, bakery yellow, decor sky, favors lilac, food mint); green for paid, red for refused.

3. Domain: party.sirinrut.com (a CNAME to Vercel, like date.sirinrut.com).
4. GitHub secret `ANTHROPIC_API_KEY` for the eval workflow.
